# ADR 002: Small decisions made while building M1 to M5

Date: 2026-11-15. Status: proposed (written by the build agent; owner to accept or amend).

## Context

The brief, ADR 001 and `docs/STRUCTURE.md` leave some details open. Each row below is a choice made during the build so the code and tests could be finished. None reopens a settled decision.

## Decisions

| # | Milestone | Question | Decision |
| --- | --- | --- | --- |
| 1 | M1 | How is "state changes only inside a tool call" enforced? | `events.record` is the only writer of run state and raises `WriteOutsideTool` unless the registry has a tool call open (`Game.tool_depth`). Replay uses the same reducer. The one exception is the `runs` row, inserted once by `new_game` before the run starts. A test scans the source for SQL writes. |
| 2 | M1 | Creating the first `game_state` row is a state change with no tool | A `start_run` engine step, registered like `end_turn` (ADR 001 #8) with audience `engine`. Engine steps live in `tools/steps.py` and are never offered to a model. |
| 3 | M1 | Where do the case's clocks, start place and nudge order live in the database? | A `case_meta` table (one row). `case_solution` also carries `min_supporting`. |
| 4 | M1 | Extra columns | `game_state.turn`, `nudge_clue`, `result`; `notebook.turn`; `events.seq`, `events.span_id`. |
| 5 | M1 | How does the no-model loop understand typed lines? | `commands.py` parses a small command grammar into a tool call and renders tool results as text. It holds no rules. |
| 6 | M1 | Name matching for `go` and `talk` | By id or name, ignoring case, punctuation and a leading "the"; a partial match counts only if unique. |
| 7 | M1 | Topic and keyword matching | A term matches at the start of a word ("boat" matches "boats"; "night" does not match "midnight"). |
| 8 | M1 | When is a find stamped, before or after the action's time cost? | After: `look` and `talk` advance the clock first, so the notebook shows the time the action ends, as in STRUCTURE example 6 (its example 1 lists the events the other way round). |
| 9 | M1 | What if a tool fails half-way? | Each registry call runs in a SQLite savepoint. An exception or an `ok: false` result rolls back everything the call wrote, so an error always means nothing changed. |
| 10 | M1 | Can actions start after 18:00 inside one turn? | No. Once the clock reaches the end of the day every game master tool returns `the day is over`; `end_turn` then ends the game. An action that starts before 18:00 may finish after it, so NPC tools inside a talk are exempt. |
| 11 | M2 | Spans versus tool rollback | Spans share the run database, so the tracer holds closed spans in memory and writes them (table and JSONL) when the root span closes, after any savepoint is released. A rejected draft inside a failed tool call is kept. |
| 12 | M2 | What is a trace? | One trace per turn (`<run_id>-t0001`, ...); work before the first turn is in `<run_id>-setup`. A `Context` always has a tracer, so no tool call can run untraced; there is one tracer per run (kept on `Game`), span ids are `<run_id>-sNNNNNN`, and a child span stays in its parent's trace. A failure to write a span is reported on stderr and never reaches the tool caller. |
| 13 | M2 | Message format between agents and `LLMClient` | A neutral dict format (`role` user / assistant / tool, `tool_calls`), documented in `llm/base.py`. Each client converts it to its provider's format. |
| 14 | M2 | Per-run JSONL files in `traces/` | Written there as the brief says, but ignored by git (`traces/*.jsonl`); the saved examples chosen in M6 are added with `git add -f`. |
| 15 | M3 | How can the game be played and tested without a model? | `offline.py` holds deterministic `ScriptedLLM` policies: a game master that understands typed commands and NPCs that recall, reveal what the engine unlocks and repeat the engine's pointer lines. `harbor play` uses them by default; `harbor play --hosted` uses `HostedLLM` for the game master, the NPCs and the referee. Both go through the same agents, tools and spans. |
| 16 | M3 | Where is a game wired together? | `session.py` (not in STRUCTURE): creates the run, tracer, NPC runner and game master. Used by the CLI, the bot and the tests. |
| 17 | M3 | Typed command grammar | `talk <person>: <words>`, `ask <person>: <words>`, `hint`, `accuse <person>: <motive> C3 C5`, plus `look`, `go <place>`, `notebook`. |
| 18 | M3 | Trust rules in detail | Levels 0 to 2, at most one change per conversation. `polite_repeat` needs an earlier line from the player to that character today and a courtesy word in the current line (`rules.COURTESY`), and counts once per character. `related_clue_shown` needs a notebook clue named in the current message (by keyword, recorded as a `clues_shown` event when said) that is a `related_clues` entry for that character, and counts once per clue. `rude` lowers by one. `unlock_if_shown` counts clues shown to that character today, as recorded when each line was said. |
| 19 | M3 | Re-revealing a clue already in the notebook | `reveal_clue` returns ok with `already_known: true` and logs `clue_confirmed`, so the referee knows that this character said it this turn. |
| 20 | M3 | What the game master returns when its loop fails | Over the 3-call cap: a fixed line asking the player to do one thing at a time, followed by the rendered results of the calls that did run. With no narration text: the tool results rendered plainly. `end_turn` runs in both cases. |
| 21 | M3 | Agent code inside `talk` | The write guard is closed while the NPC runner runs; only its own registry calls reopen it. A runner exception, an empty reply or the 4-call cap gives the character's `fallback_line` and `fallback: true`. |
| 22 | M3 | `HostedLLM` settings | `max_tokens` 4096; no thinking or sampling parameters, so any current model accepts the request; a `refusal` or `max_tokens` stop gives an empty reply with no tool calls, so `talk` uses the fallback line. The server-side refusal fallback is not set because the model is the owner's choice (`HARBOR_MODEL`). Assistant turns replay the provider's own content blocks unchanged. |
| 23 | M3 | `runs.model` | The game master's model name; `runs.prompt_hash` is the first 16 hex digits of SHA-256 over the three prompt files. |
| 24 | M3 | The game master's state summary | Carries notebook clue ids with their full text rather than titles: they are clues the player already has, and the ids let the game master map an accusation to `clue_ids`. |
| 25 | M4 | What may a reply mention? (code check) | Every clue's keywords are checked, after removing the character's own pointer lines. A match is allowed if this character revealed or confirmed the clue in this conversation, the notebook has it from this character, or the player named it in the message being answered; a keyword that also occurs in the player's message (an echo) or in the character's own persona or speech style does not count. Anything else is a leak. The model check is also told which facts the player stated. |
| 26 | M4 | The referee's model check fails how? | Open: if the check model errors, the span is marked `error` and the reply passes on the code check alone, so the game keeps going. A `LEAK` answer rejects the draft. |
| 27 | M4 | Empty or failed drafts | They go straight to the fallback line without a referee check; the fallback lines and pointer lines are tested never to trip the code check. |
| 28 | M4 | Stuck nudge details | `end_turn` arms it when `turns_since_new_clue` reaches 8 and none is armed, logged on that turn. Any new clue clears it and resets the counter. It unlocks the clue's topic but never `min_trust`. A character who neither knows the clue nor has a pointer row for it gets an engine pointer to the nearest person who knows it (`line: null`; the model phrases it). |
| 29 | M4 | `hint` target | The first unfound clue in the nudge order that someone knows; among those who know it, people not yet spoken to first, then the fewest moves away. With every nudge clue found, `target` is null. It costs 20 minutes either way. |
| 30 | M4 | A rejected draft's tool calls | Each draft attempt runs in its own savepoint. If the referee rejects it, or the attempt ends on the fallback line, what its tool calls wrote (a reveal, a trust step) is rolled back; its spans are kept. The referee runs with the write guard closed. |
| 31 | M4 | Where the prompt files are loaded | `harbor/prompts/__init__.py`, so the referee (tools layer) reads `referee.md` without importing `agents`. |
| 32 | M4 | The game master's model fails | The turn narrates a fixed error line, its agent span is `error`, and `end_turn` still runs. |
| 33 | M5 | What the ending shows | `accuse` returns the result, the clues that counted, the required clues found and missed, the culprit, the true motive and method, and the true timeline; a timeout returns the same ending from `end_turn`. Repeated clue ids count once. After an accusation, `harbor play --hosted` prints the engine's result screen itself, so the ending does not depend on the model's narration. |
| 34 | M5 | How the solver decides "points to exactly one culprit" | A clue points to the characters its text names (first name or surname). Every reachable clue counts except red herrings and alibis; the suspects are those named by at least `min_supporting` of them, and there must be exactly one, the solution's culprit. Limitation: clues that name nobody (C3, C4) are reported but cannot be weighed; an `implicates` field in the case data would fix that (docs/IDEAS.md). Reachability assumes trust can rise one step for a polite repeat and one per reachable related clue. The solver reads the loaded `Case`, not the `case_solution` table, and runs only in tests. |
| 35 | M5 | How the bot plays | Through the game master with the offline stand-ins, seeing only each turn's narration and whether the game ended: look on arrival, one generic question per person ("What did you notice last night?"), a polite repeat that shows its clues when someone holds back, follow names in replies, explore otherwise, and accuse whoever 3 notebook clues name. It is generic, not a walkthrough; the owner's walkthrough (STRUCTURE, M5) can replace its questions. `harbor bot` prints a game. |
| 36 | M5 | What "same seed" covers | Nothing in the engine draws random numbers yet; `Game.rng` is seeded from the run's seed for later use. Determinism comes from deterministic queries and the scripted models; the replay test rebuilds state from the event log alone. |
